2026-09-19 全容器化迁移与架构重构决策档案

发表于2026-09-19|更新于2026-09-20|init

定位：记录从旧裸机向全容器化架构重构搬迁的核心技术决策、设计哲学与运维防坑指南。换机器或新增 Agent 时可直接以此为顶层依据。
核心原则：「不存任何 API Key、Token 或私人群聊 ID；只沉淀可复现的架构知识、方法论与设计抉择。」


⭐一、架构底座抉择：为什么全面放弃裸机，转向 Dockge + Docker？

🥝1. 痛点驱动

  • 旧机器长期运行后散落了大量全局依赖（Node、Python、各版本 CLI、二进制后台服务及无守护进程的 CLIProxyAPI）。
  • 环境污染严重、排障困难，换机器迁移成本极高。

🥝2. 管理面板选型

  • 坚决弃用宝塔：体积臃肿、绑定全家桶、擅自改写底层系统软链与环境、黑盒逻辑重。
  • 评估并放弃 1Panel：生态稍重，对原生 docker-compose 的封装与拦截仍然较多。
  • 最终选定：Dockge + Nginx Proxy Manager (NPM)：
    • Dockge：极轻量（~30MB 内存），完全基于宿主机原生 compose.yaml 工作，Web 面板修改与终端 vim 双向秒级无缝同步，无黑盒。
    • NPM：专职负责外部域名反向代理与 Let’s Encrypt SSL 证书的自动申请与续签。

🥝3. 计算与存储物理分离铁律

  • Git 仓库必须直存于宿主机真实磁盘（/root/repos/）：绝不把代码锁死在容器内部，防止容器销毁时丢失数据，同时便于多个不同的 Agent/容器挂载协同。
  • 容器只充当“无尘车间沙盒”：通过 -v 将代码目录挂载入容器，计算在沙盒内执行，成果在宿主机落盘。

⭐二、四大容器矩阵建设（新机器落成标准）

  1. NPM 网关 (npm-app-1)：
    • 监听 80/443 及管理端口，统管二级与三级域名反代与 HTTPS 证书。
  2. Claude Code 官方沙盒 (claude-official-box)：
    • 拒绝第三方非官方镜像，严格采用 Anthropic 官方 Dev Container 规范构建（vsc-...-features-uid 完全体）。
    • 挂载持久化卷 claude-code-data，以非 root 用户 vscode 安全运行。
  3. Google Antigravity 沙盒 (antigravity-box)：
    • 基于官方脚本构建独立镜像，终端直通，环境纯净隔离。
  4. Hermes Gateway 网关中枢 (hermes-gateway)：
    • 核心通信与分身调度容器，以非 root UID 运行，挂载宿主机各 profile 配置与记忆数据库。

⭐三、🍉 “西瓜切刀”论与前端群聊解耦架构

🥝1. 核心隐喻：西瓜与切刀（业务切分边界）

  • 西瓜：代表整体业务大盘、多维资产与海量对话数据。
  • 切刀：代表组织分工与关注点分离（Separation of Concerns）。
  • 为什么不能揉成一个大西瓜？
    如果所有业务（架构总控、动画制作、海外拓客、营销视频、私人伴侣）都塞给同一个机器人单聊，不同业务的 Prompt 互相污染、上下文成倍膨胀、记忆检索严重串味，最终系统迅速退化。

🥝2. 致命陷阱：“只完成后端解耦，却忽略前端 UI 的强耦合锁死”

  • 绝大多数人设计多 Agent 时最容易掉进这个隐形坑：
    • 以为在后台配置了 4 个 Profile/分身就大功告成了；
    • 却在前端（如飞书）依然只用一个对话框或把所有 Bot 塞在一个大杂烩群里，导致人脑心智负荷极高，频繁误发指令，前端 UI 被强行锁死。

🥝3. 切西瓜真正那一刀到底在哪里？

  • 「刀不在前端飞书群手里，刀在后端的【会话 ID（Chat ID）】与【Profile 路由映射】手里！」
  • 单聊机器人有一个专属私聊 ID（p2p_chat_id）；
  • 建一个群聊，群有一个独立会话 ID（group_chat_id）。
  • 后端网关完全依靠接收到的 Chat ID 精准寻址并匹配独立 Profile 与数据空间。
  • 为什么依然强烈推荐【一业务 + 一独立群 + 一专职 Bot】（模式 A）？
    • 人脑心智物理抽屉：群名称即业务线（如 0-中枢架构、1-动画制作），天然形成视觉和操作上的分类分箱。
    • 独立看板与免打扰：每个群只接收对应业务的告警与长文本产物，不干扰其他业务。
    • 彻底双向解耦：实现了“前端人脑操作视角清晰解耦”与“后端 Agent 运行时物理隔离”的完美闭环。

⭐四、资源开销与并发真相（彻底消除虚耗顾虑）

  1. 拒绝虚胖：开 4 个专职分身，根本不需要复制 4 个庞大的 Docker 容器。
  2. 进程级监管树（s6-overlay）：
    • 官方推荐单容器多分身机制：一个 hermes-gateway 容器托管所有分身服务。
    • 闲置状态极轻：未触发对话时，CPU 占用基本为 0%，常驻内存仅几十兆。8GB 内存跑 10 个专职分身毫无压力。
  3. 独立性保障：各 Profile 在挂载卷下拥有独立配置文件与 state.db，数据互不交叉。

⭐五、人脑与大模型防遗忘对齐协议（跨机器协作铁律）

  1. Git 是跨机器跨窗口的唯一法定交换通道：
    • 本地端与远端服务器、各分身之间 AI 记忆天然互不相通；
    • 任何重要约定、架构结论与排障手册，必须落盘写进 Git 仓库并 Push，不能只留存为模型临时记忆。
  2. 严禁图片直接拖入上下文（硬规则）：
    • 单张渲染图 base64 达数百 KB 至 1MB；高频贴图极易将上下文撑爆（实测曾超 400 万 tokens），连 /compact 都无法执行；
    • 视觉校验由人类看图并用文字向 Agent 精准描述问题。
  3. 敏感凭证绝不上库：
    • 严格审查 commit 内容，严禁泄露任何 Token、密钥、内部账号或私聊 ID。
  4. 会话卫生：
    • 单任务单阶段集中沟通，阶段结束及时清理，交接与持久化永远依托仓库与规范 Commit。
